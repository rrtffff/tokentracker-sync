# 安全说明

本文件记录这个工具的安全边界、已发现的问题与修复，以及如何自行验证。
审计日期：2026-10-12。

---

## 一、威胁模型：攻击面是什么

先说清楚**不值得防的**和**值得防的**，避免过度设计。

| 维度 | 情况 |
|---|---|
| 是否联网 | ❌ 完全没有网络代码。不监听端口、不发起请求 |
| 是否提权 | ❌ 以普通用户身份运行，不申请管理员权限 |
| 是否加载外部代码 | ❌ 不 `eval`、不执行快照里的任何内容、不反序列化对象 |
| **真正的攻击面** | ✅ **「别人给你的那份数据包文件」** |

这是关键：本工具的用途就是**从别的机器拿一个文件过来导入**。
所以必须假设这个文件**可能是恶意构造的**，或者至少是损坏的。
所有安全设计都围绕这一条。

**不在威胁模型内**：本机已被入侵、攻击者能在你的用户目录里随意读写 ——
那种情况下任何用户态程序都保护不了你。

## 二、已发现的问题与修复

下面每一条都**实测复现过**，不是推测。复现方法见 `tests/security_test.py`。

### S1. 非标准 JSON 数值导致上游无法解析整行 🔴 中高

**问题**：Python 的 `json.dumps` 默认允许 `NaN` / `Infinity`，会写出字面量：

```json
{"source":"x","hour_start":"...","total_tokens":NaN}
```

但这是**非法 JSON**。上游是 JavaScript，`JSON.parse` 遇到 `NaN` 会**直接抛错**。

**实测**：
```
$ node -e 'JSON.parse("{\"total_tokens\": NaN}")'
拒绝: {"total_tokens": NaN}  ->  Unexpected token 'N'
```

**影响**：一份构造（或损坏）的数据包可以让本工具把 `NaN` 写进用户的 `queue.jsonl`，
之后 TokenTracker 读这一行会失败 —— 即**本工具破坏了用户的数据**。

**修复**：
- 写入统一走 `_dumps()`，强制 `allow_nan=False`（先整体序列化，失败就完全不落地）
- 读取时用 `parse_constant` 把 `NaN` / `Infinity` 视为损坏数据
- 导入前对每一行做数值合法性检查，非有限数直接拒绝整份数据包

### S2. 任意字段注入 🟡 中

**问题**：快照行里的任意字段会被原样搬进用户的 `queue.jsonl`。

**实测**：一份数据包里的 `kind`、`cloud_upload_owner`、`id`、`hostname_override`
等字段全部出现在了合并后的队列行里。

**影响**：`kind` 这类字段会改变 TokenTracker 对整行的解释；
伪造的 `id` 或成本字段可能影响面板显示。

**修复**：导入前按**数值字段白名单**清洗每一行（白名单来自对真实
`queue.jsonl` 的字段普查：`total_tokens`、`cost_usd`、各 `*_tokens` 等）。
不在白名单里的字段一律丢弃，**并明确告知用户丢弃了什么**（不静默）。

### S3. 键字段含 `|` 导致字段错位 🟡 中

**问题**：合并时用 `|` 把键字段拼成字符串做索引，生成合成行时**再从字符串拆回来**。
如果字段值本身含 `|`，拆分就会错位。

**实测**：`source = "a|b"` 经过一次导入后变成 `source = "a"`、`model = "b"` —— 数据损坏。

**修复**：不再反推。在扫描时**顺带记录键字段的原值**（`totals_with_parts()`），
合成行直接用原值，从根上消除这个问题。

### S4. 状态文件无上限增长 🟡 中低

**问题**：每导入一台来源机器，就把它的**全部行**永久存进 `tt-sync-state.json`，
且没有机器数上限；每次导入都要把所有历史来源重新读一遍、算一遍。

**实测**：连续导入 1~5 台（各 50 行），状态文件大小 5.5 / 11 / 16 / 22 / 27 KB —— 严格线性增长。
一份百万行的数据包会被永久保存，之后每次导入都重复处理它。

**修复**：加入 `MAX_SOURCE_MACHINES`（默认 64 台）上限，超出时明确拒绝并提示如何清理。

### S5. 快照体积 / 行数没有限制 🟡 中低

**问题**：一份超大的数据包会被整体读入内存。

**修复**：加入文件体积上限（256 MB）与单队列行数上限（30 万行），超限直接拒绝。

### S6. 备份还原的路径校验 🔵 低（已加固）

**现状评估**：原实现用 `name` 里是否含 `/`、`\`、`..` 来判断，已经挡住了典型的目录穿越。

**做得更好的地方**：改为**校验解析后的绝对路径确实落在数据目录之内**
（`os.path.commonpath`），并显式拒绝含驱动器号（`C:`）与 NUL 字符的名字。
这是纵深防御 —— 不依赖对 Windows 路径拼接边角行为的假设。

**实测结论**：`C:drv-rel.json` 这类名字在 Windows 上本来就会被规整成数据目录内的
一个普通文件，并不构成逃逸；但现在会**显式拒绝**，行为更可预测。

### S7. 损坏行不再被静默丢弃 🔵 设计修正

原实现在读取队列时会把无法解析的行直接跳过，然后写回文件 —— 等于**永久删除了**它们。

**修正**：无法解析的行作为**原始文本**保留，写回时附在文件末尾，并在导入结果里报告数量。
它们不参与统计，但不会被本工具删掉。

## 三、已确认**不是**问题（避免重复排查）

| 检查项 | 结论 |
|---|---|
| 命令注入 | 无 `shell=True`、无字符串拼接执行命令；`os.startfile` 只接收本工具自己的常量路径 |
| 任意文件读取 | 只读 `~/.tokentracker/tracker/` 下的固定文件名 + 用户显式选择的那个数据包 |
| 写到数据目录之外 | 路径来自常量与 `safe_name()` 白名单化，无外部可控成分 |
| 反序列化攻击 | 只用 `json`，不用 `pickle` / `yaml.load` / `eval` |
| 监听端口 / 远程访问 | 完全没有网络代码 |
| 凭据泄漏 | 不读取、不保存任何 API Key；`doctor` 输出可脱敏（`TT_SYNC_REDACT=1`） |
| 图片元数据泄漏 | `art/` 与 `assets/` 下所有图片均无 EXIF / XMP |

## 五、如果你想审计这份代码

按这个顺序读，20 分钟能看完：

| 文件 | 看什么 |
|---|---|
| `ttsync/core.py` → `read_snapshot()` | **唯一的外部输入入口**，所有校验都在这里 |
| `ttsync/core.py` → `sanitize_row()` | 白名单在这里 |
| `ttsync/core.py` → `_dumps()` / `write_jsonl_atomic()` | 写入出口，`allow_nan=False` |
| `ttsync/core.py` → `plan_import()` | 合并计算，无外部输入直接落地 |
| `ttsync/core.py` → `restore_backup()` → `_safe_target()` | 路径约束 |
| `ttsync/gui.py` / `cli.py` | 只做 IO 与展示，不含合并逻辑 |

**审计时可以重点确认一件事**：除了 `read_snapshot()` 与用户选择的文件路径，
是否还有其他「外部可控数据」进入写入路径。按设计应该没有。
