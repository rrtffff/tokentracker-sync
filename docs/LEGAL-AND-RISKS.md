# 法律与风险说明

这份文档把 `tt-sync` 可能涉及的法律、合规与分发风险逐条列出来，并说明当前的处理方式。
**它不是法律意见**，涉及重大决定请咨询专业人士。目的是让维护者清楚自己站在什么位置上。

## 1. 与 TokenTracker 的关系

**没有复制上游代码。** 这是最关键的一点。

- `ttsync/core.py` 是独立实现。它是通过**观察上游程序的行为与磁盘文件格式**写出来的
  （去重键是 `source|model|hour_start`、同键取最后一条、30 分钟桶等），
  没有搬运上游的任何源码、注释或数据结构定义。
- 上游 TokenTracker 采用 **MIT 许可证**。MIT 的义务是「复制或大量使用其代码时保留版权声明」——
  我们既然没有复制代码，就没有强制的署名义务。但我们仍主动在
  `THIRD_PARTY_NOTICES.txt` 中署名并链回上游仓库，这是善意做法。
- **读写别人程序产生的数据文件属于"互操作性"，不构成侵权。** 这是被广泛接受的实践
  （各种格式转换工具、兼容层、导入导出插件都属于这一类）。

### 商标问题

「TokenTracker」是上游项目的名称。我们在以下地方提到了它：

| 位置 | 用法 | 评价 |
|---|---|---|
| README 标题与正文 | 说明本工具服务于 TokenTracker | ✅ 描述性使用（nominative use），允许 |
| 窗口标题 | `tt-sync · TokenTracker 数据合并（非官方）` | ✅ 已标注非官方 |
| README 顶部免责声明 | 「非官方社区工具，与 TokenTracker 项目无关，也未获其背书」 | ✅ 必要 |
| 程序图标 / 界面 | 用的是本项目的插画，**不是**上游的 logo | ✅ |
| LICENSE 末尾 | 再次声明非官方 | ✅ |

**没有做到位的地方**：仓库名如果直接叫 `tokentracker-sync`，会相对更贴近对方商标。
这属于灰色但常见的做法（生态里大量 `vscode-xxx`、`xxx-cli` 都是这种模式），
只要不暗示官方关联、不使用其 logo，通常不会被追究。见 §2 的命名建议。

## 2. 命名建议（需要你决定）

我查了一下现状：

- PyPI 上 `tt-sync` **未被占用**（HTTP 404）
- 但 GitHub 上搜 `tt-sync` 命中 **83 个仓库**，其中 `Darkatse/TT-Sync` 已 ★34，
  名字高度接近 —— 主要是**可发现性**问题，不是法律问题

三条路，各有取舍：

| 仓库名 | 优点 | 缺点 |
|---|---|---|
| `tt-sync` | 短、干净 | 和已有项目撞名，搜索容易被淹没 |
| `tokentracker-sync` | 搜 TokenTracker 的人**一定能找到** | 名字里含他人商标（常见做法，风险低） |
| `tt-usage-merge` / `ttmerge` | 完全避开商标 | 可发现性差，别人搜不到 |

**我的建议**：`tokentracker-sync`。理由是这个工具的用户 100% 来自 TokenTracker 用户群，
可发现性比"名字干净"重要得多；而且描述性使用他人产品名来说明兼容性是通行做法，
只要 README 第一屏就有非官方声明即可（我们已经有了）。

**但这是品牌决定，你自己拍板。** 如果要改名，告诉我，我改完顺手把 README 里的链接也更新掉。

## 3. ⚠️ 角色插画版权（最高风险，未解决）

`art/mascot.jpg` 是当前 GUI 背景、窗口内吉祥物和程序图标的来源。
`assets/` 下的图片都是由它生成的派生作品。

**风险**：如果这张图不是你原创、也不是明确允许再分发的素材（例如来自画师的
"禁止商用/禁止转载"作品、或来源不明），把它放进公开仓库 + 打包进 exe 发布，
可能触发 DMCA 下架，严重时会影响账号。

**解决方式（任选其一）**：

1. **换成你自己的素材** —— 把新图命名为 `art/mascot.jpg` 覆盖，然后运行：
   ```bash
   python packaging/make_assets.py
   ```
   背景图、角色图、图标会全部重新生成。

2. **换成明确可商用的素材** —— 例如 CC0 图库、或你委托画师并要求了商用授权
   （保留授权凭证）。

3. **直接删掉图片** —— 删除 `art/` 和 `assets/` 里的 png/ico：
   ```bash
   rm -rf art assets
   ```
   界面会自动降级为无背景图（`gui.py` 里对图片加载做了 try/except），
   功能完全不受影响。发布一个纯功能项目也是完全可以的。

**判断方法**：如果这张图是网上随手存的、或者 AI 生成但使用的模型/平台对输出物的
商用授权不明确，就按"有风险"处理。

## 4. 第三方组件许可

发布 exe 时，二进制里打包了这些组件。结论：**全部允许自由再分发，没有传染性许可问题。**

| 组件 | 许可证 | 是否随 exe 分发 | 影响 |
|---|---|---|---|
| CPython 3.12 | PSF License | 是 | 宽松，需保留声明 |
| Tcl/Tk 8.6 | Tcl/Tk License（BSD 类） | 是 | 宽松，需保留声明 |
| tkinterdnd2 | MIT | 是 | 宽松 |
| tkdnd | Tcl/Tk 类宽松许可 | 是 | 宽松 |
| **PyInstaller bootloader** | **GPLv2 + 特殊例外** | 是 | ⚠️ 见下 |
| Pillow | MIT-CMU | **否**（仅构建期） | 无 |

**关于 PyInstaller 的 GPL**：很多人会担心"用 GPL 工具打包，我的程序是不是也得 GPL"。
**不会。** PyInstaller 的许可证是「GPLv2 **附加一个特殊例外**」，该例外明确允许
用它构建并分发任意许可的程序（包括闭源商业程序）。而且打包只是把 bootloader
嵌进可执行文件，产物不构成 PyInstaller 的衍生作品。所以本项目的 MIT 许可是成立的。

**已做的合规动作**：仓库根目录有 `THIRD_PARTY_NOTICES.txt`，列明上述组件与许可。
发布 Release 时建议把它一起作为附件（或至少保证仓库里可见）。

## 5. 隐私与数据

**本程序没有任何联网代码。** 已逐文件核查（`ttsync/*.py`）：

- 唯一的网络相关 import 是 `socket`，只用于 `socket.gethostname()` 取本机名（纯本地调用）
- 没有 `urllib` / `requests` / `http` / `socket.connect` 等任何出网调用
- 不写任何日志到外部、不上报遥测

它读什么、写什么：

| 行为 | 内容 |
|---|---|
| 读 | `~/.tokentracker/tracker/` 下的数据文件（只有 token 数字、时间、模型名、数据源名） |
| 写 | 同上（合并后的 `queue.jsonl`、备份文件、`tt-sync-state.json`） |
| 导出包内容 | 上述数据 + **主机名** + **machineId**（一个哈希值）+ 合并规则说明 |

值得注意的是：**导出包里带三类可识别信息**，分享给别人前要留意。

| 字段 | 内容 | 为什么必须有 | 怎么去掉 |
|---|---|---|---|
| `machine.hostname` | 你的电脑名 | 方便人/界面区分"这是哪台机器导出的" | 手工改成 `"PC-A"` 之类，不影响功能 |
| `machine.machineId` | 一个哈希值 | 防止"把自己导出的包导回自己"导致重复计数 | 删掉后失去这层保护，但合并仍正确 |
| `queues.projects[].project_key` | **项目目录路径**（如 `C:\Users\你\work\某项目`） | 项目维度的用量统计需要它 | 删掉整个 `projects` 段落即可，只影响项目视图 |

**最容易漏掉的是第三项**：`project.queue.jsonl` 里存的是项目路径，属于会暴露你
目录结构、甚至工作内容性质的信息。如果你把导出包贴到 issue 里求助，
建议先把 `projects` 部分删掉。

另外提醒一层：用量数据本身会暴露「你什么时候、用什么 AI 工具、用了多少」。
如果这台是你**公司配的电脑**或**实习期间使用的设备**，这类数据的分享需要更谨慎。

如果你要把导出包发给别人排查问题，可以用 `doctor` 的脱敏输出（`TT_SYNC_REDACT=1` 会把 machineId 只留后 6 位）。

## 6. 与上游付费云服务的边界

上游把"跨设备合并"作为付费 Cloud 的卖点（$4.99/月）。本工具免费实现了同类效果，
这**不违法**（本地文件互操作），但需要明确边界：

| 我们做了 | 我们没做 |
|---|---|
| 读本机自己的数据文件 | ❌ 不访问、不调用上游的任何服务器或 API |
| 写本机自己的数据文件 | ❌ 不绕过任何鉴权、不伪造身份、不抓取他人数据 |
| 建议用户关闭云同步 | ❌ 不破坏、不干扰上游服务的运行 |

**一个需要如实告知用户的副作用**：导入会重写 `queue.jsonl`，并把它对应的
`queue.state.json` 的 `offset` 置 0（因为这个字节偏移是针对旧文件的）。
如果用户当时**开着云同步**，这会触发一次全量重新上传。上传的是**用户自己的**数据，
到**用户自己的**账号，所以不构成数据外泄；但这确实会消耗对方服务器的资源。
因此程序默认在检测到云同步开启时**拒绝导入**，这也是最稳妥的默认行为。

## 7. 分发实操风险

这些不是法律问题，但会直接影响别人能不能顺利装上：

| 现象 | 原因 | 缓解 |
|---|---|---|
| Windows SmartScreen 拦截「未知发布者」 | exe 未做代码签名 | 在 Release 里附 **SHA256 校验值**，并说明可从源码自建 |
| 杀软误报 | PyInstaller 单文件 exe 是启发式扫描的常见目标 | 同上；也可提供免安装的源码方式 |
| 用户担心安全性 | 从网上下来一个会改本地数据的 exe | README 已写明「无联网 + 导入前自动备份 + 可回滚」；`doctor` 命令可自检 |

**建议做法**：发布 Release 时同时上传 `SHA256SUMS.txt`，README 里加一句
「有疑虑可自行 `python packaging/build_windows.bat` 构建」。

## 8. 数据损坏的责任

- LICENSE 是 MIT，已包含完整的**免责条款**（不提供担保、不承担损害赔偿责任）
- 技术上也做了防护：
  - 每次导入前自动备份原文件（`queue.jsonl.bak-ttsync-*`）
  - 备份/还原是"单文件 + 字节级"，还原前还会把当前数据另存一份
  - 写入用「临时文件 + 原子替换」，不会写坏一半
  - 控制记录与无法识别的行**原样透传**，不静默丢弃数据
- 已知限制（最近 1 小时桶可能短暂偏小）也已写进 README，属于"已披露"状态

## 10. 如果你有学生 / 在职身份，额外注意两件事

这两条不是"这个项目特有的"，而是所有个人开源项目都会碰到的通用问题，
但因为你的情况比较特殊，值得单独提一下。

### 10.1 职务作品 / 职务发明

如果你在**实习单位或学校的实验室**里、用**单位设备和时间**开发了这个项目，
或者项目内容与你的工作职责直接相关，部分司法辖区（包括中国《专利法》《著作权法》
及相关司法解释）可能认定成果属于**职务作品/职务发明**，权利归单位。

**建议**：
- 明确这是**个人项目**——在工作时间之外、用个人设备开发
- 别在项目里引用你单位的内部资料、代码、文档
- 如果这个工具和你实习内容沾边（比如你实习就在做 AI 工具相关的东西），
  稳妥的做法是先跟导师/主管口头说明一下，避免日后扯不清

### 10.2 上游作者也是个人开发者

TokenTracker 的维护者是一个个人开源作者（不是大公司）。
这意味着：

- 对方**不太可能**真的发起法律行动，但也意味着你的项目可能直接影响他一个人的收入
  （Cloud 订阅）
- 所以 §9 的"打个招呼"更有意义——这是**同行之间的礼貌**，而不只是风险规避

如果对方明确表示不希望有这类工具，尊重他的意愿、把仓库设为 private 是成本最低的选择。
技术上你随时可以私有化（`git` 历史都在本地，不会丢）。
